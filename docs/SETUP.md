# Shift Sync — установка и настройка

Пошагово: конфигурация, запуск, подключение Google Календаря с доступом
ровно к одному календарю и ни к чему больше.

> Без Google сервис запускается и работает целиком, кроме записи в календарь:
> вход, загрузка, распознавание, экран проверки. Google подключается разделом 4.

---

## 1. Что нужно на машине

| | Проверить | Версия |
|---|---|---|
| Node 22 | `node -v` | 22.x |
| pnpm 10 | `pnpm -v` | 10.x |
| Docker | `docker --version` | с Compose v2 |
| PostgreSQL | поднимается контейнером | порт 5481 |

## 2. Конфигурационные файлы

### Какие файлы есть

| Файл | Что это | Состояние |
|---|---|---|
| `.env.example` | **шаблон** с комментариями по каждой переменной | в репозитории |
| `.env` | **рабочая конфигурация** | создаётся из шаблона, только локально |
| `secrets/service-account.json` | ключ сервисного аккаунта Google | только локально, раздел 4 |
| `infrastructure/systemd/*.service` | шаблоны автозапуска | в репозитории |
| `docker-compose.yml` | сборка и запуск всего вместе | в репозитории |

`.env` и `secrets/` в `.gitignore` — в репозиторий не попадут.

### Первая настройка

```bash
cp .env.example .env
# пароль для входа и секрет сессии — случайные строки
sed -i "s/^APP_PASSWORD=.*/APP_PASSWORD=$(openssl rand -base64 18)/" .env
sed -i "s/^SESSION_SECRET=.*/SESSION_SECRET=$(openssl rand -base64 32)/" .env
grep '^APP_PASSWORD=' .env   # этим паролем входить
```

Обязательных полей два — `APP_PASSWORD` и `SESSION_SECRET`. Для записи в календарь
дополнительно нужны `GCAL_CALENDAR_ID` и файл `secrets/service-account.json` (раздел 4).

**Без Google сервис всё равно работоспособен**: вход, загрузка кадров, распознавание,
экран проверки. Не работает только кнопка «Применить» — она честно откажет с понятным
сообщением и **ничего не запишет в базу**.

### Пересоздать конфигурацию с нуля

```bash
cp .env.example .env
# затем задать APP_PASSWORD и SESSION_SECRET, например так:
python3 -c "import secrets; print('APP_PASSWORD=' + secrets.token_urlsafe(12))"
python3 -c "import secrets; print('SESSION_SECRET=' + secrets.token_urlsafe(32))"
```

### Все переменные

**Относительные пути считаются от рабочего каталога backend — `apps/api`** (D-019).
В Docker пути абсолютные, там вопрос не возникает.

| Переменная | Что делает | По умолчанию |
|---|---|---|
| `NODE_ENV` | режим: `development` \| `production` \| `test` | `development` |
| `PORT` | порт сервиса | `4080` |
| `LOG_LEVEL` | подробность лога: `fatal`…`trace` | `info` |
| **`APP_PASSWORD`** | **пароль для входа. Обязателен** | — |
| **`SESSION_SECRET`** | **подпись cookie-сессии, минимум 16 символов. Обязателен** | — |
| `SESSION_TTL_DAYS` | сколько дней живёт сессия | `30` |
| `COOKIE_SECURE` | `true`, если сервис за HTTPS | `false` |
| `DB_HOST` `DB_PORT` `DB_NAME` `DB_USER` `DB_PASSWORD` | подключение к PostgreSQL | `localhost:5481/fc_shift_sync` |
| `DB_DEBUG` | печатать SQL в лог | `false` |
| `DB_AUTO_MIGRATE` | применять миграции при старте | `true` |
| `STORAGE_DIR` | куда складывать кадры | `../../storage/screenshots` |
| `SCREENSHOT_RETENTION_DAYS` | сколько хранить кадры; `0` — удалять сразу | `180` |
| `OCR_MAX_SIDE_LENGTH` | до какого размера ужимать кадр перед распознаванием | `1280` |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | путь к ключу | `../../secrets/service-account.json` |
| **`GCAL_CALENDAR_ID`** | **ID целевого календаря** | — |
| `GCAL_TIMEZONE` | часовой пояс смен | `Europe/Helsinki` |
| `GCAL_UPDATE_STRATEGY` | `update` — менять событие на месте, `recreate` — удалять и создавать | `update` |
| `GCAL_EVENT_PREFIX` | заголовок события: «Работа 08:00–14:00» | `Работа` |
| `GCAL_COLOR_ID` | цвет события, 1…11 | `11` |
| `GCAL_APP_TAG` | метка «своих» событий. **Менять нельзя**, иначе сервис перестанет узнавать ранее созданные события | `fc-shift-sync` |

### Про `OCR_MAX_SIDE_LENGTH`

Единственная настройка распознавания. Кадры из ORTEC — 590×1280, и `1280` означает
«не сжимать вообще». Именно на этом значении получен результат 9 из 9. Уменьшать
смысла нет: скорость и так ~104 мс на кадр, а качество упадёт.

### Переменных `RECOGNITION_*`, `OLLAMA_*`, `GEMINI_*` не существует

Их **нет ни в коде, ни в конфигурации**. Проверить можно так:

```bash
grep -rE "RECOGNITION_|OLLAMA_|GEMINI_" apps/ packages/ tools/ --include=*.ts
# ничего не найдёт
```

Провайдер распознавания один — PP-OCRv5 через `ppu-paddle-ocr`. Переключать нечего,
поэтому переключателя нет. Кадры и выгрузки обрабатываются локально и наружу не уходят
вообще: единственный внешний запрос за всё время жизни сервиса — разовое скачивание
весов модели (~15 МБ) при первом распознавании снимка. Выгрузке PDF не нужно и его:
она читается по текстовому слою файла, без распознавания.

Раньше эти переменные фигурировали в черновике архитектуры, когда рассматривался
запасной уровень на облачной модели. От него отказались (`DECISIONS.md`, D-004),
из кода всё убрано.

## 3. Как запускать

### База данных

```bash
pnpm db:up      # поднять PostgreSQL на порту 5481
pnpm db:down    # остановить
```

Данные лежат в томе `fc-postgresql-data` и переживают перезапуск.

### Вариант А. Всё в Docker — так и надо в обычной жизни

```bash
docker compose up -d --build
```

Поднимет базу и приложение, применит миграции, откроет `http://localhost:4080`.

```bash
docker compose logs -f app     # смотреть лог
docker compose up -d           # применить правку .env (пересоздаёт контейнер)
docker compose restart app     # просто перезапустить, .env при этом не перечитывается
docker compose down            # остановить всё
```

### Вариант Б. Одним процессом, без Docker

```bash
pnpm db:up
pnpm build                      # contracts → web → api
node apps/api/dist/main.js      # http://localhost:4080
```

Backend сам раздаёт собранный фронт: один порт, отдельный процесс для фронта не нужен.

### Вариант В. Разработка, два процесса

```bash
pnpm db:up
pnpm --filter @fc/contracts build
pnpm --filter @fc/api dev       # backend на 4080, перезапуск при правках
pnpm --filter @fc/web dev       # фронт на 4081, прокси /api на 4080
```

Открывать `http://localhost:4081`.

### Автозапуск при включении компьютера

```bash
sudo cp infrastructure/systemd/shift-sync.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now shift-sync

systemctl status shift-sync
```

Есть и вариант без Docker — `shift-sync-node.service`, ему нужна отдельно поднятая база.

### Удалить созданное сервисом

Чтобы пройти сценарий с чистого листа или отменить неудачный импорт:

```bash
pnpm --filter @fc/api run purge -- --all              # показать, что удалится
pnpm --filter @fc/api run purge -- --all --yes        # удалить
```

**Без `--yes` это сухой прогон** — печатает список и выходит, ничего не трогая.

Фильтр задаётся по рабочим датам смен, и под удаление попадает всё, что сервис
создал для этих дат: события в календаре, смены, распознанные строки, лог, а
следом кадры и загрузки, от которых ничего не осталось.

| Фильтр | Что берёт |
|---|---|
| `--all` | все даты |
| `--from=2027-03-01 --to=2027-03-31` | диапазон, обе границы включительно |
| `--date=2027-03-07` | конкретную дату, флаг можно повторять |

`--from/--to/--date` складываются: дата подходит, если совпала хоть с одним.
Область по умолчанию — и календарь, и база; можно сузить до `--calendar` или `--db`.

**Убрать одну загрузку из истории** — когда фильтр по датам не годится, потому что
несколько загрузок покрывают одни и те же дни:

```bash
pnpm --filter @fc/api run purge -- --batches                    # список загрузок
pnpm --filter @fc/api run purge -- --batch=<id> --yes           # убрать одну
```

`--batch` удаляет только саму загрузку: её кадры и распознанные строки. Смены и
события в календаре остаются — их могла подтвердить и другая загрузка; для них
есть фильтр по датам.

**Чужие события не пострадают.** Выборка идёт по метке `app=fc-shift-sync` фильтром
на стороне Google — личные события в неё физически не попадают, — и метка
проверяется ещё раз перед удалением каждого события. Файл кадра удаляется, только
когда на него не осталось ни одной ссылки в базе: одинаковые кадры из разных
загрузок хранятся одним файлом. У загрузки PDF файлов два — отрисованная страница и
исходная выгрузка, — и ссылкой считаются оба.

### Остановить, если порт занят

```bash
ss -ltnp | grep :4080          # найти процесс
kill <pid>
```

⚠️ Не использовать `pkill -f "node dist/main.js"` — шаблон совпадёт с самой командой,
и она убьёт себя вместе с оболочкой.

## 4. Google: сервисный аккаунт с доступом к одному календарю

### Почему это безопасно по своей природе

Сервисный аккаунт — **отдельная личность**, не связанная с вашим Google-аккаунтом.
У неё свой пустой календарь, свой пустой Drive, и она **не видит ничего**, что ей
явно не открыли. Вы не даёте сервису доступ к своему аккаунту — вы создаёте новую
учётку и открываете ей ровно один календарь.

Ограничение работает на трёх уровнях, и каждый достаточен сам по себе:

| Уровень | Что ограничивает |
|---|---|
| **Область (scope)** | сервис запрашивает только `calendar.events`. С ней нельзя ни создать календарь, ни удалить, ни поменять права — только события внутри доступных календарей |
| **Включённые API** | в проекте включается только Google Calendar API. Запрос к Drive или Gmail вернёт ошибку, даже если бы токен позволял |
| **Что расшарено** | только календарь «Смены». Остальные календари семьи сервисный аккаунт не видит |

### Шаг 1. Проект в Google Cloud

1. Открыть [console.cloud.google.com](https://console.cloud.google.com/).
2. Создать проект, например `shift-sync`.
3. **APIs & Services → Library** → найти **Google Calendar API** → **Enable**.

> Больше **ничего не включать**. Ни Drive API, ни Gmail API, ни People API.
> Чем меньше включено, тем меньше поверхность.

### Шаг 2. Сервисный аккаунт

1. **IAM & Admin → Service Accounts → Create service account**.
2. Имя: `shift-sync`. Описание: «запись рабочих смен в календарь».
3. **Шаг «Grant this service account access to project» — пропустить.**
   Роли не нужны ни одной: аккаунт не обращается к ресурсам проекта.
4. **Шаг «Grant users access» — тоже пропустить.**
5. Создать.

### Шаг 3. Ключ

1. Открыть созданный аккаунт → вкладка **Keys** → **Add key → Create new key → JSON**.
2. Файл скачается сам. Положить его в проект:

```bash
mv ~/Downloads/shift-sync-*.json secrets/service-account.json
chmod 600 secrets/service-account.json
```

3. Скопировать адрес аккаунта — он в поле `client_email` внутри файла и на странице
   аккаунта. Вид: `shift-sync@<id-проекта>.iam.gserviceaccount.com`.

```bash
grep client_email secrets/service-account.json
```

### Шаг 4. Открыть доступ только к одному календарю

1. Открыть [calendar.google.com](https://calendar.google.com) под аккаунтом, где лежит календарь «Смены».
2. Слева навести на календарь **«Смены»** → **⋮** → **Настройки и общий доступ**.
3. Раздел **«Открыть доступ определённым пользователям или группам»** → **Добавить пользователей**.
4. Вставить адрес сервисного аккаунта.
5. Права — **«Внесение изменений в мероприятия»**.

   > Не «Изменение мероприятий **и настроек доступа**». Второй уровень позволил бы
   > сервису менять права самого календаря, а ему это не нужно.

6. Отправить.

**Больше ни один календарь на этот адрес не открывать.**

### Шаг 5. ID календаря

На той же странице настроек прокрутить до раздела **«Интеграция календаря»** →
скопировать **Идентификатор календаря**. Выглядит как
`<длинный-id>@group.calendar.google.com` (у основного календаря это просто адрес почты).

```dotenv
GCAL_CALENDAR_ID=<длинный-id>@group.calendar.google.com
```

### Шаг 6. Проверить, что доступ ровно такой, какой нужен

```bash
pnpm --filter @fc/api run check:google
```

Скрипт покажет, что сервис **умеет** и, главное, **чего не может**:

```
── Что сервис умеет ────────────────────────────────────────────
✓ читает события целевого календаря
✓ видит свои события по метке app=fc-shift-sync

── Чего сервис НЕ может (так и должно быть) ────────────────────
✓ не может: получить список всех календарей аккаунта (403)
✓ не может: создать новый календарь (403)
✓ не может: изменить права доступа к календарю (403)
✓ не может: обратиться к Google Drive (403)
```

Проверить конкретный посторонний календарь — передать его ID аргументом:

```bash
pnpm --filter @fc/api run check:google -- <id-другого-календаря>@group.calendar.google.com
```

Если скрипт скажет «ДОСТУП ЕСТЬ» — этот календарь тоже расшарен, доступ надо убрать.

### Чего не делать

| | Почему |
|---|---|
| Не включать **Domain-wide delegation** | Это единственная настройка, которая дала бы сервисному аккаунту право действовать от имени других пользователей. Для нашей задачи не нужна и категорически вредна |
| Не выдавать аккаунту роли IAM в проекте | Ему не нужна ни одна |
| Не включать лишние API | Каждое включённое API — расширение поверхности |
| Не открывать на него другие календари | Ровно один, «Смены» |
| Не коммитить `secrets/service-account.json` | Каталог в `.gitignore`, но проверяйте перед коммитом |

### Как отозвать доступ

Любого из трёх действий достаточно:

1. **Быстро:** в настройках календаря «Смены» удалить сервисный аккаунт из списка доступа.
   Сервис мгновенно перестанет видеть календарь.
2. **Надёжно:** в Google Cloud удалить ключ на вкладке Keys — файл станет бесполезен.
3. **Совсем:** удалить сервисный аккаунт целиком.

Ранее созданные события останутся в календаре — их можно найти по заголовку «Работа».

### Что будет видно в календаре

События создаются от имени сервисного аккаунта, поэтому в карточке события
организатором будет он, а не владелец календаря. На отображение в сетке и на напоминания
это не влияет.

## 5. Проверка, что всё работает

```bash
# 1. база отвечает
docker exec fc-postgresql pg_isready -U fc_admin -d fc_shift_sync

# 2. сервис отвечает
curl -s http://localhost:4080/health
# {"status":"ok","db":true}

# 3. фронт отдаётся
curl -s http://localhost:4080/ | grep -c '__nuxt'
# 1

# 4. тесты
pnpm --filter @fc/api test        # 78 тестов
pnpm --filter @fc/contracts test  # 9 тестов, словари

# 5. качество распознавания на эталонных кадрах
pnpm bench                        # Совпало: 9/9

# 6. доступ к Google (после раздела 4)
pnpm --filter @fc/api run check:google
```

Затем — открыть `http://localhost:4080`, войти по паролю из `.env`, загрузить
синтетические образцы из `samples/ess/` (скриншоты) или `samples/pdf/` (выгрузки)
и посмотреть экран проверки.

## 6. Доступ с телефона

Скриншоты делаются на телефоне, поэтому загружать их удобно оттуда же.

### По локальной сети

С телефона в той же сети сервис открывается по адресу машины:

```
http://<адрес-машины>:4080
```

Сервис слушает на `0.0.0.0`, снаружи доступен сразу, ничего настраивать не нужно.
Узнать адрес машины:

```bash
ip -4 addr show | grep -oP 'inet \K[\d.]+' | grep -v 127.0.0.1
```

Чтобы адрес не менялся, стоит закрепить его в роутере по MAC-адресу.

### Вне дома — через Tailscale

Если на машине поднят Tailscale, достаточно поставить его на телефон и войти в тот же
аккаунт — после этого сервис открывается откуда угодно по имени машины в tailnet:

```
http://<имя-машины>.<tailnet>.ts.net:4080
```

Трафик шифруется, наружу в интернет ничего не торчит. Самый удобный вариант,
когда телефон не дома.

⚠️ **Не выставлять сервис в интернет напрямую без HTTPS.** Пароль уходит открытым
текстом. Если всё же нужно — поставить перед ним обратный прокси с сертификатом
и включить `COOKIE_SECURE=true`.

## 7. Если что-то не так

| Симптом | Что смотреть |
|---|---|
| `APP_PASSWORD обязателен` при старте | `.env` не найден или поле пустое. Файл ищется в `apps/api/.env`, `apps/api/.env.local` и в корне проекта |
| `Google Календарь не настроен` | `GCAL_CALENDAR_ID` пуст или нет `secrets/service-account.json`. Запустить `check:google` |
| `check:google` не находит ключ | путь в `GOOGLE_SERVICE_ACCOUNT_JSON` считается от `apps/api`, значение по умолчанию — `../../secrets/service-account.json` |
| События не появляются | календарь открыт на адрес аккаунта с правом «Внесение изменений»? `check:google` покажет |
| Порт 4080 занят | `ss -ltnp \| grep :4080`, затем `kill <pid>` |
| Батч завис в «распознаётся» | логи `OcrService`: при первом запуске качаются веса ~15 МБ |
| Хочется начать с чистого листа | `pnpm --filter @fc/api run purge -- --all --yes` — уберёт и события в календаре. `docker compose down -v` сносит только локальные данные, календарь не трогает |
